# 转换与上板恢复规则

适用于转换失败、数值分歧、资源/路由失败、执行恢复和代理完成验收。依据新上板六模型及 Nexys Video BN 修复记录维护。门禁、原始模型和历史 run 均保持冻结；实验的监控策略保存在该实验任务记录，不作为技能默认策略。

## 开始前

- 先读同模型最近成功/失败记录、兼容补丁和阶段证据，记录本次采用的 skill 文件哈希。可复用诊断结论；新产物仍需本次验证。
- Windows 使用短的 model-id/run-id 和输出根目录。检查预计的 HLS、仿真和 Vivado 深层文件路径；长路径支持开关不能保证所有 EDA 子工具兼容。
- `model.input_shape` 包含 batch 维；如 NHWC 图像为 `[1,25,25,1]`。在转换前核对模型实际输入形状和冻结样本形状；不能通过删掉 batch 检查修正输入准备错误。
- 对比顶层契约与 `hls_config` 中的精度、Strategy、ReuseFactor、逐层 ReuseFactor。同一参数冲突即具名失败，先生成明确的新契约再重试。

## 数值分歧

1. 保留失败 run、完整输出和逐值比较。用首个分歧定位输入量化、乘积、累加、偏置、激活和输出类型。
2. QKeras 内部量化来自原模型；只将最终 HLS 图输出映射到契约接口网格。不可统一扩大内部层或修改权重来掩盖分歧。
3. `quantized_po2` 检查生成的 `weight_exponential::r_T`：指数位数决定移位范围，中间乘积必须保留该范围内的整数与小数位。hls4ml 1.3.0 的已知模板修复仅作用于新生成工程，记录版本、前后哈希；未知模板拒绝自动修改。
4. 完整 `hls_config` 应传入转换，并核对 `parameters.h`/`defines.h`。hls4ml 1.3.0 的 `TableType` 不控制实际查找表类型，实际键是 `Table_t`。保留冻结请求并明确告警；不能静默改名后宣称原契约执行成功。
5. 修复后按 CSim → CSynth 生成 RTL → 板级仿真 → Vivado 综合/实现推进；每步通过才继续。容差、样本覆盖、精度、时钟和资源上限不得因失败而放宽。

## 流接口与面积归因

- 输入 payload 位宽与核心 TDATA 端口位宽分别计算。输入 N 拍、输出单拍的适配器只适用于每 N 个接受输入拍按序产生一个输出拍的核；先以实际核心仿真确认此性质。
- 请求从完整输入窗口边界开始；空闲窗口填零以保持 dataflow 核运行。只在握手后推进元素和窗口计数；背压下 TVALID/TDATA 保持稳定；输出按窗口序号关联。
- 输出多拍、非整除 lane、不同元素/slot 网格等仍明确拒绝；禁止伪造 wrapper 几何或删除检查来绕过适配器能力限制。
- ROM 流包装使用按元素排序的窄同步读 ROM，并使 registered data 与 valid 对齐。多 lane 地址为 `sample_index * input_elements + element_index + lane`；数组接口继续使用每样本一个宽字。
- 实现拥堵或面积超限先读综合后的层级利用率、关键路径和拥堵区域。输入 ROM/mux、transport、adapter 的逻辑可能被综合合入核心层级；不能仅凭实例名称或 HLS 估计断言模型过大。
- 避免对整个输入 payload 做可变移位、宽并行装载移位寄存器，或用除法计算运行时窗口序号。接口包装修复、逐层合法 RF/stream 契约变体、实现后物理优化应分别验证，不能一次混改后归因。
- 边缘负 WNS 仍是失败。可在新实现尝试中采用有证据支持的 post-route phys_opt，再 route 并重查 WNS/WHS、资源和端口；不能将某模型成功参数自动推广到其他模型。

## 时序候选是否生效

- 先将 routed 最差 source/destination 映射到实际函数/config 与算子，再读对应的 HLS XML、RTL、逻辑/路由延迟和扇出。顶层 HLS 估计与 routed 路径不一定指向同一层；换板后的封装/速度等级、约束与调度差异也须核对。
- 工具接受选项、源码拆循环或少量 RTL 文件哈希变化，不代表流水边界生效。检查真实寄存器/进程/通道、调度和算子绑定；仅行号或符号变化不支持“修复有效”。无有效结构变化的源码候选不重复等价 EDA；物理策略变更独立记录依据。
- normalize 的局部进程拆分、算子映射或控制网调整须保留乘积位宽、截断点、加法顺序及协议。模板影响的全部实例都要记录；完整仿真通过后才物理验证。具体判别与已验证案例见 [timing-closure-debugger](../timing-closure-debugger/SKILL.md)，不默认给所有 BN 打 DATAFLOW 补丁。

## 监控与恢复

- 区分代理、监督器与 EDA 子进程状态。为当前阶段记录 `request_id`、`model_id`、`run_id`、`stage`、`attempt_id`、真实起止、PID/子进程、日志更新及产物进展。复合 `host-build` 下的 synth/impl/bitstream 分别记录；launcher 起点不代表当前子阶段起点。以实际命令、进程创建时间及日志/证据相互核对，轮询和消息不改写原开始时间；缺失起点标记未知并要求执行者补证。
- 监控/恢复动作按当前任务明确授权的策略执行；技能不设固定时长的自动介入或强杀规则。工具自身的诊断 timeout 单独记录。日志活跃不能证明门禁通过，日志安静也不能单独证明死锁；综合检查进程 CPU、日志、产物与退出状态，对健康 EDA 继续等待。终止仅针对经诊断需要停止的该任务进程树，保留现场；禁止按进程名批量杀进程或启动重复任务。
- 暂停/恢复以最新用户指令和本次请求归属为准。当前请求的 `PAUSED` 且 `paused_by_user=true` 是合法终态，保留已完成门禁并停止后续硬件执行；不能把暂停当缺证反复催代理 finish。用户明确继续后，旧请求的暂停文件/结果只作历史，新的结果必须匹配当前 `request_id`/`followup_request_id` 和实际 run。
- executor 异常先读错误、监督器状态与保存会话；确认无仍活的原任务后，用当前任务对应的监督器、原 `conversation_id` 和本次范围恢复。委托执行模式下，监控者仅发送针对性输入，不另启转换或硬件任务；已核验 PASS 模型不重复构建/烧录。
- 恢复优先补缺失阶段或重跑受影响阶段。失败阶段的重跑使用新 run 并保存复用来源与哈希，不能覆盖失败证据；同 run 仅补尚未执行的阶段。仅当契约、核心、模板/适配器、约束及其哈希与该阶段依赖一致，才复用上游产物；变化影响的下游门禁必须重做。单改 UART 包装无需重新训练或重新做无变化的 HLS 转换。
- 代理 `FINISHED` 仅表示代理停了。按用户目标验收同一 run 的证据：全部冻结样本/全部输出、板级仿真、routed 资源、setup/hold 时序、DRC、端口审计、JTAG、完整 UART 帧和 Python/HLS 双数值门；实时采集须 `attempt_complete=true`。逐样本拼接原始接收块、校验帧长度/序号/CRC，并核对解码值与输出文件。核验位流、DCP、端口审计、program summary、采集 provenance/manifest 的哈希及实际 JTAG/UART 桥身份；参考的 canonical-values 哈希不能冒充文件哈希，来源路径为空不单独判失败，先查 provenance。
- 缺证时先列具体缺失：报告漏汇总、比较未执行、执行失败或哈希失配分别处理。只补受影响项，要求产生可核验的变化；同一缺失无进展时保留 `INCOMPLETE_EVIDENCE` 和具体原因，不反复发送无变化的 finish/续跑输入。控制器应记录补证尝试和停止原因。
- 后续部署受共享 skill 改动影响时，使用新 run、新产物和新的来源哈希验证受影响阶段。历史上板结果仍是历史事实，但不是新版构建已重新烧录的证明；只改技能说明不需要为宣称文档已更新而重复烧录。
